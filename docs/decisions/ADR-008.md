# ADR-008: Self-Registration Restricted to OPERATOR

## Status
Accepted

## Context
The public registration endpoint accepted a `role` field and stored it verbatim (`RegisterRequest` → `User.role`). This meant any anonymous caller could register an account with the `ADMIN` role and gain full platform access. RBAC is meaningless if roles are user-choosable.

## Decision
- The public `POST /api/auth/register` endpoint **always** creates `OPERATOR` accounts; any supplied role is ignored.
- Higher-privileged roles (`ENGINEER`, `MAINTENANCE_ENGINEER`, `MANAGER`, `ADMIN`) are provisioned only by:
  - the startup seed data (`SeedDataInitializer`, gated by `SEED_DEFAULT_USERS`), or
  - direct database administration.
- Duplicate username/email returns a `400` instead of a generic server error.

## Consequences
- **Pros**: Removes the privilege-escalation vector. Keeps registration simple (users do not need to understand roles). The role model remains intact for administrator-provisioned accounts.
- **Cons**: Operators cannot be self-promoted; an admin action (or seed / DB change) is required to grant elevated roles. The requirement for a separate admin-provisioning flow is deferred (acceptable for V1, see ADR-006).
