# ADR-003: Why pgvector

## Status
Accepted

## Context
We need a vector database to store document chunk embeddings and perform similarity search (k-NN or HNSW). Options include specialized vector databases (Pinecone, Milvus, Qdrant) or extensions to existing relational databases.

## Decision
Use PostgreSQL with the `pgvector` extension.

## Consequences
- **Pros**: Reduces infrastructural complexity. We can store the relational document metadata (permissions, authorship, versions) alongside the embeddings in the same database. This allows us to perform RBAC filtering efficiently within the SQL query itself (see ADR-005).
- **Cons**: May not scale to billions of vectors as efficiently as a specialized database like Milvus, but for an engineering documentation platform (thousands to millions of vectors), pgvector provides excellent performance.
